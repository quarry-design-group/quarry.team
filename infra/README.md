# Infrastructure (`infra/`)

Production-grade Terraform that provisions the `quarry.team` marketing-site
stack on **Cloudflare**, plus the Worker runtime secrets it generates (the
Turnstile widget secrets), which the GitHub provider writes into the
repository's deploy environments (`github.tf`). It is designed to be run from a
GitHub Actions workflow (`terraform init / plan / apply`) once credentials are
supplied as repository secrets.

The site itself — the prerendered static pages **and** the same-origin `/api/*`
form endpoints — builds to a single **Cloudflare Worker (Static Assets)** via
the `@astrojs/cloudflare` adapter and is shipped by **`wrangler deploy`** (see
`.github/workflows/deploy-web.yml`), _not_ Terraform. Terraform owns the
stateful/config plane: the zone config, **D1**, **R2**, **Turnstile**, and the
**WAF/rate-limit** rulesets. See ADR-0006, ADR-0008, ADR-0014. Cache policy is
not Terraform-managed — see the note under the table.

> **No secrets are committed.** Every token is read from an environment
> variable / GitHub Actions secret or generated by a provider. The example
> tfvars contains placeholders only.

## What this provisions

### Cloudflare (the whole stack)

| Resource                                                     | Purpose                                                                                                                                                                                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data.cloudflare_zone`                                       | Looks up the **existing** `quarry.team` zone by name. The zone is assumed to already exist.                                                                                                                               |
| `cloudflare_d1_database` (`marketing-site-form-submissions`) | **D1** (SQLite at the edge) — the durable store for contact + careers form submissions. Bound to the Worker as `DB`. Backups via Time Travel.                                                                             |
| `cloudflare_d1_database` (`…-staging`)                       | Staging counterpart — staging and PR-preview test submissions never touch production data (ADR-0013).                                                                                                                     |
| `zero_trust_access_application` + policy (staging ZTNA)      | The whole staging host behind Cloudflare Access — `@quarry.team` emails only (OTP by default; pages and `/api/*` both gated).                                                                                             |
| `cloudflare_ruleset` (staging noindex)                       | `X-Robots-Tag: noindex, nofollow` response header on `staging.quarry.team` — the soak host never enters search indexes.                                                                                                   |
| `cloudflare_zone_setting` (email obfusc.)                    | **Scrape Shield** email obfuscation `on` — Cloudflare rewrites emails/`mailto:` in proxied HTML. Belt-and-suspenders with `Email.astro`.                                                                                  |
| `cloudflare_r2_bucket` (`quarry-tf-state`)                   | **Terraform remote state.** Bootstrapped out-of-band; see below.                                                                                                                                                          |
| `cloudflare_turnstile_widget` (`…-forms`)                    | Managed-mode bot protection for the contact/careers forms. Its secret is set as the Worker secret `WORKER_TURNSTILE_SECRET`.                                                                                              |
| `cloudflare_turnstile_widget` (`…-grievances`)               | **Invisible-mode** widget for the stakeholder grievance form — no puzzle, no checkbox (ADR-0017). Secret → `WORKER_TURNSTILE_GRIEVANCES_SECRET`.                                                                          |
| `github_actions_environment_secret` (x4)                     | `WORKER_TURNSTILE_SECRET` and `WORKER_TURNSTILE_GRIEVANCES_SECRET` in the `staging` and `production` GitHub environments, valued from the two widgets (`github.tf`); every deploy ships them to the Worker.               |
| `cloudflare_ruleset` (WAF custom)                            | Challenge suspicious traffic to `/api/*`; challenge high-threat POSTs. (Canonical hosts are enforced by `workers_dev = false` in `apps/web/wrangler.toml`, not here — a zone ruleset never sees `*.workers.dev` traffic.) |
| `cloudflare_ruleset` (rate limit)                            | Per-IP rate limit (3 per 10s) on the form POSTs: `/api/*` and the on-demand `/policies/grievances` page — the burst layer; the Worker adds a D1 throttle with progressive backoff.                                        |
| `cloudflare_ruleset` (www redirect)                          | 301 `www` → apex at the edge (canonical host), path + query preserved.                                                                                                                                                    |

The WAF threat-score cutoffs and the rate-limit envelope are public in this
HCL by choice. The controls behind them do not depend on the numbers staying
private: Turnstile verifies every submission, the forms carry a honeypot, and
the Worker's D1 throttle backs off repeat grievance submissions over the hour.

**Cache policy is not here, and cannot be.** Every hostname on this zone is
served by a Worker (apex/`www`/`staging` via wrangler custom-domain routes;
`docs` via the `quarry-docs` Worker), and Cloudflare is explicit that
[no zone cache configuration applies to Workers](https://developers.cloudflare.com/workers/cache/):
Cache Rules, Cache Response Rules, Page Rules and cache level settings "have no
effect on a Worker's cache". A `cloudflare_ruleset` in the
`http_request_cache_settings` phase was carried here until 2026-09-19 and never
did anything; it was retired rather than left as a plausible-looking decoy. The
single cache plane for this site is **`apps/web/public/_headers`**, whose
`Cache-Control` values the Worker's asset layer serves verbatim.

**The Worker** (`quarry-web`, plus `quarry-web-staging` on `staging.quarry.team`)
is built and deployed by wrangler, not Terraform. It binds the D1 database
(`DB`), serves `dist/client` as static assets, and runs the `/api/contact` +
`/api/careers` routes plus the on-demand `/policies/grievances` pages
(ADR-0017). apex + `www` (and `staging`) custom-domain DNS is
managed by the Worker's `routes` in `apps/web/wrangler.toml` on deploy.

**Web Analytics:** enabled on the zone via **automatic injection** (carried
over from the legacy site — dashboard-managed, not Terraform, and no in-repo
snippet: the edge injects the beacon into proxied HTML). The repo's only job
is the CSP allowlist in `apps/web/public/_headers`
(`static.cloudflareinsights.com` script + `cloudflareinsights.com` connect) —
without it the injected beacon would be silently blocked. Notes: injection is
zone-wide, so `staging.quarry.team` traffic also reports (filter by hostname
in the Web Analytics dashboard); `*.workers.dev` preview URLs bypass the zone
and are never counted.

**Security headers:** delivered via the committed `apps/web/public/_headers`
file (CSP, HSTS, etc.), served by the Worker's static assets — kept in source
control alongside the content it protects, not in Terraform.

## Provider versions

| Provider                | Version constraint | Notes                                                                  |
| ----------------------- | ------------------ | ---------------------------------------------------------------------- |
| `cloudflare/cloudflare` | `~> 5.0`           | v5 is the OpenAPI-generated rewrite (object-style nested attributes).  |
| `integrations/github`   | `~> 6.13`          | Environment secrets only (`github.tf`), authenticated as a GitHub App. |
| Terraform               | `>= 1.10.0`        | Native S3-backend lockfile locking (`use_lockfile`) against R2.        |

The exact provider versions are locked in `.terraform.lock.hcl`, committed with
Linux, Windows, and macOS hashes, so every plan, drift check, and apply runs
the same providers. Dependabot's `terraform` group raises the lock within each
major line as a pull request, held by the cooldown
([ADR 0018](../docs/adr/0018-dependency-update-policy.md)). Every Dependabot
PR that touches `infra/` (or the Infra workflow) gets a **strict**
`terraform plan`: it runs with the read-only
[Dependabot secrets](#dependabot-secrets) and `-detailed-exitcode`, so any
diff fails the required **Terraform plan** check and holds the auto-merge the
`immediate` tier armed. A bump that plans `No changes` merges on its own. A
provider that adds a defaulted attribute plans an in-place update (5.26.0 did
this to `cloudflare_turnstile_widget`, see `modules/cloudflare-web/main.tf`),
so its PR stops red. That is provider churn, not live drift. Read the plan in
the PR's run; if the diff is the expected churn, merge the PR by hand (an
admin can merge past the red check) and reconcile with one `apply` dispatch
from `main`. Unrelated live drift fails the plan too, and the PR waits until
that drift is reconciled. To change a
provider by hand: `terraform init -upgrade` in `infra/`, then `terraform
providers lock -platform=linux_amd64 -platform=windows_amd64
-platform=darwin_arm64 -platform=darwin_amd64`, and commit the lock.

The definition has been applied and reconciled against the v5 provider since
2026-06: staging and production run from it, and a weekly scheduled `terraform
plan` fails on any drift between this HCL and the live zone.

## Bootstrap (one-time, before the first `init`)

1. **Create the R2 state bucket** (`wrangler r2 bucket create quarry-tf-state`).
2. **Create an R2 S3 API token** (Cloudflare → R2 → Manage API Tokens, _Object
   Read & Write_) → `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`.
3. **Create a Cloudflare API token** → `CLOUDFLARE_API_TOKEN`, with:
   - **Zone (quarry.team only):** Zone Read, DNS Write, Workers Routes Write,
     Zone WAF Write (WAF custom + rate-limit rulesets),
     Access: Apps and Policies Write (staging ZTNA), Dynamic URL Redirects
     Write (www→apex canonical-host rule),
     Transform Rules Write (staging noindex header), Zone Settings Write
     (email obfuscation). Zone rulesets need these zone-scoped, phase-specific
     groups — account-ruleset permissions do NOT cover them.
   - **Account:** Workers Scripts Write, D1 Write, Workers R2 Storage Write,
     Turnstile Sites Write, **Access: Apps and Policies Write**. The staging
     ZTNA is two resources at two scopes — the application is zone-scoped
     (`cloudflare_zero_trust_access_application.staging`, `zone_id`) but the
     reusable policy it references is created at the account
     (`cloudflare_zero_trust_access_policy.staging_team`, `account_id`) — so
     this one permission is granted at **both** scopes; a Zone-only grant risks
     failing the from-zero apply on the policy.
4. **Ensure the `quarry.team` zone already exists** in the account.

### Importing the state bucket

The state bucket is declared in `modules/cloudflare-storage` behind
`manage_state_bucket` (`false` in `main.tf`), so Terraform leaves the
bootstrapped bucket alone until it is imported. To bring it under management
(drift-tracked, `prevent_destroy`), from `infra/` with the backend initialized
(see [Locally](#locally)):

1. Set `manage_state_bucket = true` on the `storage` module in `main.tf`, and
   set `r2_location_hint` (the default in `variables.tf` and the value in the
   local tfvars) to the bucket's actual location (Cloudflare → R2 →
   `quarry-tf-state` → Settings) so the plan proposes no change to it.
2. Import it (the v5 import id is `<account_id>/<bucket_name>/<jurisdiction>`;
   a bucket created without a jurisdiction is `default`):

   ```sh
   terraform import -var-file=environments/production.tfvars \
     'module.storage.cloudflare_r2_bucket.state[0]' \
     "${CLOUDFLARE_ACCOUNT_ID}/quarry-tf-state/default"
   ```

3. Run `terraform plan -var-file=environments/production.tfvars` and confirm it
   reports no changes for `module.storage`, then commit the `main.tf` change
   through a PR so CI's plans and the weekly drift check see the same
   definition.

## Plan / apply

### CI (`infra.yml`)

The **Infra (Terraform)** workflow plans on infra PRs, runs the weekly drift
check, and applies only on a manual `workflow_dispatch` with `apply`. Its job
is the required **Terraform plan** check, so it runs on every PR (no `paths`
filter): its first step plans only a PR that touches `infra/` or `infra.yml`,
skips fork PRs (they receive no secrets), and passes the rest in seconds. A
human PR's plan is informational; a Dependabot PR's plan is strict (see
[Provider versions](#provider-versions)). The R2
credentials reach the s3 backend as `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY` environment variables (from the `R2_*` secrets), the
GitHub provider authenticates as the Terraform GitHub App through
`GITHUB_APP_ID` / `GITHUB_APP_INSTALLATION_ID` / `GITHUB_APP_PEM_FILE` (from the
`TERRAFORM_GITHUB_APP_*` variables and secret), the account id reaches
Terraform as `TF_VAR_cloudflare_account_id`, and every other variable takes its
committed default, so no var-file is passed:

```sh
terraform init -input=false \
  -backend-config="bucket=quarry-tf-state" \
  -backend-config="key=quarry-team/production.tfstate" \
  -backend-config="endpoints={s3=\"https://${CLOUDFLARE_ACCOUNT_ID}.r2.cloudflarestorage.com\"}"

terraform plan  -input=false                      # manual plans
terraform plan  -input=false -lock=false          # human PRs (read-only: no state lock)
terraform plan  -input=false -lock=false -detailed-exitcode  # Dependabot PRs: any diff fails the check
terraform plan  -input=false -detailed-exitcode   # weekly drift check: any diff fails the run
terraform apply -input=false -auto-approve        # manual dispatch with `apply` only
```

### Locally

For an ad-hoc plan, supply the same credentials and the account id through a
local tfvars file (gitignored):

```sh
cd infra
cp environments/production.tfvars.example environments/production.tfvars   # fill cloudflare_account_id

export CLOUDFLARE_API_TOKEN=…        # the provider token
export AWS_ACCESS_KEY_ID=…           # R2_ACCESS_KEY_ID
export AWS_SECRET_ACCESS_KEY=…       # R2_SECRET_ACCESS_KEY
export CLOUDFLARE_ACCOUNT_ID=…
export GITHUB_APP_ID=…               # TERRAFORM_GITHUB_APP_ID
export GITHUB_APP_INSTALLATION_ID=…  # TERRAFORM_GITHUB_APP_INSTALLATION_ID
export GITHUB_APP_PEM_FILE="$(cat terraform-github-app.pem)"   # the App's private key (Passbolt)

terraform init \
  -backend-config="bucket=quarry-tf-state" \
  -backend-config="key=quarry-team/production.tfstate" \
  -backend-config="endpoints={s3=\"https://${CLOUDFLARE_ACCOUNT_ID}.r2.cloudflarestorage.com\"}"

terraform plan -var-file=environments/production.tfvars
```

The GitHub provider needs the App credentials to refresh the environment
secrets already in state; without them it runs anonymously and the plan fails
at refresh. Applies go through the gated CI dispatch.

### Wiring the outputs

After the first apply, wire the Worker to the databases Terraform created (the
apply's "Terraform outputs (post-apply)" log prints them):

```sh
terraform output -raw d1_database_id          # → wrangler.toml [[d1_databases]].database_id
terraform output -raw d1_staging_database_id  # → wrangler.toml [env.staging] d1 binding
```

Then the **Deploy Web** workflow builds and ships the Worker:

```sh
# staging (CLOUDFLARE_ENV selects [env.staging] at build time; ADR-0013):
CLOUDFLARE_ENV=staging SITE_URL=https://staging.quarry.team pnpm --filter @quarry/web build
cd apps/web
wrangler d1 migrations apply marketing-site-form-submissions-staging --remote -c dist/server/wrangler.json
wrangler deploy -c dist/server/wrangler.json

# production (every push to main that touches the site, behind DEPLOY_ENABLED):
SITE_URL=https://quarry.team pnpm --filter @quarry/web build
cd apps/web
wrangler d1 migrations apply marketing-site-form-submissions --remote -c dist/server/wrangler.json
wrangler deploy -c dist/server/wrangler.json
```

### Worker runtime secrets

The Worker's runtime secrets live in the `staging` and `production` **GitHub
environments** (never committed, never set on the Worker by hand). Every
Deploy Web run hands its secrets step the `worker-secrets` map in
`.github/workflows/deploy-web.yml`, which names each `WORKER_*` secret and
nothing else, writes them to a file (`.github/scripts/worker-secrets.mjs`), and
deploys with `wrangler deploy --secrets-file`. Repository and organization
secrets never reach that step. A Worker secret carries the same `WORKER_*`
name in GitHub, in the map, on the Worker, and in the code that reads it, and
this table lists exactly the map's names; `apps/web/src/lib/worker-secrets-map.test.ts`
holds the code, the map, `github.tf`, and this table to one another. A secret
the environment does not hold keeps its current value on the Worker.
Step 5 of the [bootstrap runbook](../docs/runbooks/bootstrap.md) sets them.

| Secret                                | Source                  | Purpose                                                                                                   |
| ------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------- |
| `WORKER_TURNSTILE_SECRET`             | Terraform (`github.tf`) | Server-side Turnstile verification for the contact/careers forms; a deployed build without it answers 503 |
| `WORKER_TURNSTILE_GRIEVANCES_SECRET`  | Terraform (`github.tf`) | The invisible grievance widget's secret (ADR-0017)                                                        |
| `WORKER_RESEND_API_KEY`               | `gh secret set`         | Submission-notification email (also the grievance acknowledgments)                                        |
| `WORKER_FORM_SUBMISSIONS_IP_HASH_KEY` | `gh secret set`         | HMAC key for the stored client-address hash (ADR-0014); distinct from `WORKER_GRIEVANCE_SIGNING_KEY`      |
| `WORKER_GRIEVANCE_SIGNING_KEY`        | `gh secret set`         | REQUIRED: grievance form token + IP hashing (ADR-0017); a production Worker without it serves a 503 form  |
| `WORKER_NOTION_TOKEN`                 | `gh secret set`         | Grievance log mirror (Notion internal integration)                                                        |
| `WORKER_GRIEVANCE_NOTIFY_BACKUP_TO`   | `gh secret set`         | REQUIRED for routing: the backup's OWN inbox, never the shared alias                                      |
| `WORKER_FORM_SUBMISSIONS_NOTIFY_TO`   | `gh secret set`         | Optional (default hello@quarry.team)                                                                      |
| `WORKER_FORM_SUBMISSIONS_NOTIFY_FROM` | `gh secret set`         | Optional (default "Quarry Site <noreply@quarry.team>")                                                    |
| `WORKER_FORM_SUBMISSIONS_WEBHOOK_URL` | `gh secret set`         | Optional                                                                                                  |
| `WORKER_GRIEVANCE_NOTIFY_TO`          | `gh secret set`         | Optional (default concerns@quarry.team)                                                                   |

The two Turnstile secrets are managed by Terraform: `github.tf` holds a
`github_actions_environment_secret` per environment and secret, valued from
the widget resources, through the GitHub provider authenticated as the
Terraform GitHub App (`GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`,
`GITHUB_APP_PEM_FILE`; installation tokens last an hour, and the App holds only
Environments: read and write on this repository). The provider encrypts each value client-side, so
it never passes through a shell or a job log; plans and the drift check read
only metadata (GitHub never returns a secret's value), which is enough to flag
an environment secret edited or deleted outside Terraform. The value sits in
state beside the widget resource that already carries it. The next deploy
ships a rotated secret; run Deploy Web after an apply that rotates one.

`PUBLIC_TURNSTILE_SITE_KEY` and `PUBLIC_TURNSTILE_GRIEVANCES_SITE_KEY` are
**build-time** vars (baked by Astro) — set them in the Deploy Web workflow from
`terraform output turnstile_sitekey` / `turnstile_grievances_sitekey`.

### Dependabot secrets

A workflow run that Dependabot triggers sees **only** the repository's
Dependabot secrets (Settings → Secrets and variables → Dependabot), never the
Actions secrets above, and gets a read-only `GITHUB_TOKEN`. The Infra workflow
plans Dependabot PRs with the same secret names, so the values stored here are
**read-only** credentials. A Dependabot plan runs the new provider binary
before anyone has reviewed it, so it gets credentials that can read the
account and the state but change neither. PR plans run with `-lock=false`, so
no write to the state bucket is needed.

| Secret                                 | Value                                                                                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `CLOUDFLARE_API_TOKEN`                 | A separate token with the same resource scope as the Actions one, every permission at **Read** ([bootstrap §1](../docs/runbooks/bootstrap.md#1-create-the-repository-secrets) lists them). |
| `CLOUDFLARE_ACCOUNT_ID`                | The account id (same value as the Actions secret).                                                                                                                                         |
| `R2_ACCESS_KEY_ID`                     | A separate R2 S3 API token, **Object Read only**, scoped to the `quarry-tf-state` bucket.                                                                                                  |
| `R2_SECRET_ACCESS_KEY`                 | That token's secret.                                                                                                                                                                       |
| `TERRAFORM_GITHUB_APP_PEM`             | Private key of the **Terraform Plan** GitHub App (Environments: **read** only), not the read-write Terraform App.                                                                          |
| `TERRAFORM_GITHUB_APP_ID`              | The Terraform Plan App's id. A secret here only because Dependabot runs cannot rely on repository variables.                                                                               |
| `TERRAFORM_GITHUB_APP_INSTALLATION_ID` | The Terraform Plan App's installation id (same reason).                                                                                                                                    |

The workflow reads the App ids as `secrets.X || vars.X`: Dependabot runs take
the plan App's ids from these secrets, and every other run, which has no such
secret, falls through to the repository variables. If a secret here is missing
or rejected, `terraform init` or the plan fails and the PR stays red: the gate
fails closed.

### GitHub Actions **variables**

Repository variables (Settings → Secrets and variables → Actions →
Variables). The four gates below switch on the workflows that act on
Cloudflare or need code scanning: each is off while unset, `true` turns it on,
and unsetting it is the emergency stop.

| Variable                 | Gates                                                                               | Set to `true` at                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `STAGING_DEPLOY_ENABLED` | `deploy-web.yml` staging job; `preview-web.yml` (PR previews)                       | [bootstrap](../docs/runbooks/bootstrap.md) §6, once staging's infra and secrets exist         |
| `DOCS_DEPLOY_ENABLED`    | `deploy-docs.yml`; `preview-docs.yml`                                               | bootstrap §7, bringing up `docs.quarry.team`                                                  |
| `DEPLOY_ENABLED`         | `deploy-web.yml` production job (apex/`www`, post-deploy smoke and rollback)        | bootstrap §9, the production go-live                                                          |
| `ENABLE_CODEQL`          | `codeql.yml` Analyze job (PRs, pushes and its weekly schedule; skipped while unset) | bootstrap §1, once code scanning is available (public repository or GitHub Advanced Security) |

Two more variables identify the Terraform GitHub App for `infra.yml`:
`TERRAFORM_GITHUB_APP_ID` and `TERRAFORM_GITHUB_APP_INSTALLATION_ID`, beside the
`TERRAFORM_GITHUB_APP_PEM` secret (bootstrap §1). Dependabot runs use the
read-only Terraform Plan App instead, from [Dependabot secrets](#dependabot-secrets).

## How it maps to the stack

- **Astro site** (`apps/web`) → built with `@astrojs/cloudflare`; prerendered
  pages to `dist/client`, the Worker to `dist/server`. Deployed as one Cloudflare
  Worker (Static Assets) by `wrangler deploy`.
- **Forms** → same-origin `/api/contact` + `/api/careers` routes on that Worker,
  Turnstile-verified, persisted to **D1** (`DB` binding).
- **Grievances** → the on-demand `/policies/grievances` page on that Worker
  (invisible Turnstile, D1 `grievances` tables, Notion mirror) — ADR-0017.
- **State** → R2 (`quarry-tf-state`) via the S3-compatible backend.
